## Preamble

This document defines the formal notation used by the Viable System Framework (VSF)
to encode systems, rules, memory, and inter-system communication.

The notation has two audiences:
- **Humans:** read the annotated form (notation +
// comment
)
- **Machines (LLMs, parsers):** read the pure notation form (no comments required)

Version declaration is mandatory in every
.vsm
 file:

    @vsm 0.1          // toda máquina o humano debe verificar esto primero
                      // Human: every .vsm file must declare its spec version

## Part II — Axioms

Axioms are the non-derivable truths of the system.
They cannot be proven from within the framework — they are the foundation.

### A1 — Recursion axiom

    S1(L) = { V_i(L+1) }_{i=1}^{n}

    // Human: every operational unit of S1 at level L is itself a complete
    // viable system at level L+1. This is what makes the model scale-invariant.
    // You cannot have a "partial" viable system — it either is one, or it isn't.

### A2 — Budget monotonicity axiom

    B(L+1) ≤ B(L)    ∀L

    // Human: a child system never has more resources than its parent.
    // This guarantees the recursion terminates — you cannot infinitely subdivide
    // a finite budget. Both tokens and compute obey this.

### A3 — Physical resource axiom

    B(L) = min( B_tokens(L), B_compute(L), B_time(L) )

    // Human: the effective budget is the most constrained dimension.
    // Token budget and thermal budget are the same *type* of thing —
    // finite physical resources that the system must account for.
    // Neither can be borrowed from the future.

### A4 — Channel axiom (no direct coupling)

    ∀ V_i(L+1), V_j(L+1) where i ≠ j:
      V_i ↛ V_j    // no direct channel between siblings
      V_i → φ↑ → S3(L) → φ↓ → V_j    // all sibling communication via parent S3

    // Human: siblings cannot talk directly. All communication goes through
    // the parent's S3. This prevents the system from developing hidden
    // dependencies that the parent cannot observe or regulate.

### A5 — Autonomy ceiling axiom

    ∀ op ∈ S1(L):
      op.autonomy ≤ S5(L).ceiling

    // Human: no operational unit can exceed the autonomy declared by S5.
    // Single-loop corrections (fix within rules) may be automated.
    // Double-loop corrections (change the rules) ALWAYS require human approval.
    // A system that violates this is not a viable system — it is a rogue process.

### A6 — Ashby's requisite variety

    Var(E(L)) ≤ Var(S3(L)) ⊕ Var(S2(L))

    // Human: the system can only regulate disturbances it has enough
    // variety to match. If the environment is more varied than the regulator,
    // the system cannot maintain viability and must escalate (A7).

### A7 — Escalation axiom

    signal s escalates from L+1 to L  iff:
      resolve(s, V(L+1)) = ∅  ∧  urgency(s) > τ_{L+1}

    // Human: a signal escalates when the current level cannot resolve it
    // AND it exceeds the local resolution threshold. Both conditions required.
    // A signal that is resolvable locally but urgent stays local.
    // A signal that is not resolvable but not urgent may be deferred.

### A8 — Absorption invariant

    |S(L)| ≤ |S(L+1)| · (1 − r_L)    r_L ∈ (0,1)

    // Human: the volume of signals decreases exponentially as you move up levels.
    // With r=0.9 (90% local resolution), the grandparent sees 1% of grandchild signals.
    // This is what keeps the root-level opsroom actionable at any system scale.

## Part III — Definitions

Definitions are derived from axioms. They can be verified.

### D1 — Viable System

    V(id, L) ::= ⟨ S1, S2, S3, S4, S5, E ⟩ @ level=L

    // Human: a viable system is identified by a name and a level.
    // The six components are always present — if any is missing, the system
    // must declare itself non-viable until resolved.

### D2 — Upward channel

    φ↑ : V_i(L+1) → S3(L)
    φ↑.payload = events.jsonl
    φ↑.schema  = connection_schema.json @ "upward"

    // Human: every child system writes to events.jsonl.
    // The parent S3 reads it. This is the only legitimate upward path.

### D3 — Downward channel

    φ↓ : S3(L) → V_i(L+1)
    φ↓.payload = params.json
    φ↓.schema  = connection_schema.json @ "downward"

    // Human: the parent S3 writes params.json for each child.
    // The child reads it at startup. No other configuration source is valid.

### D4 — Budget allocation (S3 bargain)

    B_i = B(L) · w_i / Σ_j w_j    where w_i = priority_weight(V_i)

    // Human: S3 distributes the level's total budget proportionally by priority.
    // The sum of all child budgets equals the parent budget (conservation).
    // w_i comes from params.json — it is set by the parent, not the child.

### D5 — Recursion condition

    is_viable(u) = True   iff  complexity(u) > τ_viability
    is_viable(u) = False       // u is a leaf — execute_atomic(u)

    // Human: a unit is recursed into only if it's complex enough to warrant
    // its own S1-S5 structure. Simple units execute atomically (no LLM, no S4).
    // τ_viability is set by the parent S3 in params.json.

### D6 — LLM constraint

    S4(L).uses_LLM = True   only if L ≤ L_max
    L_max = 2               // current system default

    // Human: language models are only used at cognitive layers (L2 and above).
    // L0 (tool execution) and L1 (scheduling) are pure Python — no LLM in the loop.
    // This is not a performance optimization — it is a variety constraint.
    // LLMs have high variety; using them at L0 would violate A6 for that level.

### D7 — Opsroom mapping

    opsroom(V(id, L)) = {
      view["system_health"]    ≡ S3(L).audit,        // physical resource state
      view["pipeline_status"]  ≡ S1(L).operations,   // units running/stopped
      view["signal_queue"]     ≡ S2(L).unresolved,   // signals not locally absorbed
      view["priority_ranking"] ≡ S4(L).environment,  // current environment model
      view["coverage_gaps"]    ≡ S3(L) → S4(L)       // model vs. reality delta
    }

    // Human: the opsroom is not a separate tool — it IS the VSM made visible.
    // The five views map 1:1 to the five subsystems. Any opsroom for any domain
    // has exactly these five views; only E(L) (the environment) varies.
    // The opsroom is also where the human operator exercises A5 (autonomy ceiling).

### D8 — Signal priority classes

    urgency(s) ∈ { CRITICAL, HIGH, MEDIUM, LOW }

    CRITICAL : resolve(s, V(L))=∅  ∧  urgency(s)=CRITICAL  ⟹  s escalates immediately
    HIGH     : present to operator at current level before next tick
    MEDIUM   : log + inform operator, resolve within session
    LOW      : absorb locally, log only

    // Human: only CRITICAL and HIGH signals appear in the opsroom Signal Queue.
    // MEDIUM signals appear as informational. LOW signals are invisible at this level
    // but visible at the level that generated them. This implements A8.

### D9 — Calibration score

    CalibScore(V, t) = (T_expected(V) / T_actual(V,t)) · (B_used / B_allocated)

    CalibScore ≈ 1.0  →  system behaves as modeled
    CalibScore < 0.7  →  bottleneck detected — inspect S3 telemetry
    CalibScore > 1.3  →  model is pessimistic — recalibrate T_expected

    // Human: used by the calibration runner service to benchmark the pipeline.
    // Both time efficiency and resource efficiency must be close to 1.
    // A system that is fast but wasteful, or efficient but slow, is miscalibrated.

## Part IV — Grammar (BNF)

    system      ::= "@vsm" version NL declaration+
    declaration ::= system_def | rule_def | channel_def | memory_def

    system_def  ::= "V(" id "," "L=" int ")" "=" "{" subsystems "}"
    subsystems  ::= subsystem ("," subsystem)*
    subsystem   ::= "S1:" unit_list
                  | "S2:" coord_spec
                  | "S3:" regulate_spec
                  | "S4:" intel_spec
                  | "S5:" policy_spec
                  | "E:"  env_spec

    unit_list   ::= "[" (id | system_def) ("," (id | system_def))* "]"

    rule_def    ::= "rule(" subsystem_ref "," "guard=" guard "):" NL body+
    guard       ::= condition | "∅"
    condition   ::= expr "<" expr | expr ">" expr | expr "=" expr
    body        ::= "  " "∀" quantified | "  " "∃" quantified | "  " action

    channel_def ::= "φ" direction "(" source "→" target "):"  NL
                    "  payload=" file_ref NL
                    "  schema="  schema_ref
    direction   ::= "↑" | "↓"

    memory_def  ::= memory_type "(" id "):" NL field+
    memory_type ::= "episodic" | "semantic" | "procedural" | "policy"
    field       ::= "  " key "=" value

    version     ::= int "." int

## Part V — Translation rules (Human ↔ VSM)

### 5.1 From prose to VSM

| Prose pattern | VSM notation |
|---------------|--------------|
| "always do X before Y" |
rule(S3, guard=∅): X ∘ Y
 |
| "never do X directly, use Y" |
∀ op: op.X ∘ Y  // direct X prohibited
 |
| "if condition, then escalate" |
condition ⟹ φ↑(signal, urgency=HIGH)
 |
| "X depends on Y being done" |
X.prereq = Y.status == done
 |
| "confirm before destructive action" |
op ∈ S5.ceiling.requires_confirm
 |
| "priority order: A, B, C" |
S5.priorities = [A, B, C]
 |
| "use tool X for task Y" |
S1.unit["Y"].tool = X
 |

### 5.2 From VSM to human

VSM is read left-to-right, level by level:

1.
@vsm 0.1
 → "this is a VSM spec, version 0.1"
2.
V("X", L=0)
 → "X is a root-level viable system"
3.
S1: [a, b, V("c", L=1)]
 → "operations are: a, b, and c (c is itself a full system)"
4.
φ↑(V_i → S3)
 → "child i reports upward to parent coordination"
5.
rule(S3, guard=temp<59): launch ∘ scheduler
 → "S3 rule: only launch through scheduler when temp<59°C"
6.
s ⟹ φ↑
 → "signal s escalates to parent"

### 5.3 What does NOT compress well

The following remain in prose and are referenced by symbol, not inlined:

- **Why** explanations (historical context, incident post-mortems)
- **Tradeoff narratives** (why option A over option B)
- **Onboarding context** (what the system is for, in natural language)

These are stored as
@ref prose_doc
 in the VSM file and kept in full prose separately.

## Part VI — Memory encoding

### 6.1 Feedback memory (compressed form)

    // BEFORE (prose, ~200 tokens):
    // "Never launch remote jobs directly — always route through the thermal scheduler.
    //  Why: The scheduler kills processes when CPU > threshold. Direct launch = SIGTERM
    //  under load. Lesson learned from a session where three concurrent jobs caused
    //  a thermal spike and data loss."

    // AFTER (VSM, ~45 tokens):
    @vsm 0.1
    rule(S3["my-platform"], guard=temp<threshold_c):
      ∀ op ∈ S1.remote: launch(op) ∘ thermal_scheduler
      violation: SIGTERM @ temp≥threshold_c
      @ref why="feedback_scheduler_rule.prose.md"    // full narrative kept separately

### 6.2 Project memory (compressed form)

    // BEFORE (prose, ~350 tokens):
    // "VSF framework, score 93%, decisions D1-D9, L0-L3 architecture..."

    // AFTER (VSM, ~80 tokens):
    @vsm 0.1
    semantic("vsf-architecture"):
      version  = "0.2"
      lifecycle = iterating
      decisions = [D1..D10]              // @ref HANDOFF.vsm.md#decisions
      levels   = {L0: tool-conductor, L1: pipeline-scheduler,
                  L2: [cognitive-layer, token-economy], L3: vsf-meta}
      tasks    = [C, D, E, F, G, H]     // @ref TASKS.vsm
      public   = {license: MIT, lang: EN, status: pre-release}

### 6.3 System config (compressed form)

    // BEFORE (CLAUDE.md, ~1500 tokens)
    // AFTER (VSM, ~180 tokens):
    @vsm 0.1
    V("my-system", L=0) = {
      E:  { host: "local", runtime: "python3.11", infra: "redis+postgresql" },
      S1: { units: [unit-a, unit-b, unit-c],
            pipeline: phase-0 → phase-1 → phase-2 → phase-3 },
      S2: { anti_loop: "5 retries → escalate",
            log: "~/logs/my-system/" },
      S3: { scheduler: thermal_scheduler, guard: temp<threshold_c,
            confirm: ["irreversible", "shared-state", "external"] },
      S4: { opsroom: briefing_script,
            signals: {HIGH: resolve_first, MED: inform_user} },
      S5: { ceiling: { double_loop: requires_human },
            priorities: [mission_A, mission_B, mission_C],
            lang: { public: EN } }
    }

## Part VII — Machine interface

Instructions for any LLM loading a
.vsm
 file:

1. **Read
@vsm
 version first** — if version unknown, halt and report
2. **Axioms are constraints** — A1-A8 are never overridden by local rules
3. **Rules are ordered** — higher S-number = higher authority (S5 > S3 > S1)
4. **
@ref
 pointers are lazy** — load the referenced document only if needed
5. **Compression is lossy for narrative, lossless for rules** — rules encoded in VSM
   are complete; narrative content requires following
@ref
 links
6. **When writing VSM:** minimize tokens, use symbols over words, use
@ref
 for prose
7. **When translating VSM to human:** expand symbols using Part V table,
   read rules as imperative instructions, read axioms as hard constraints

% ABSTRACT
% -----------------------------------
\begin{abstract}
We present a formal notation for the Viable System Model (VSM) as a computational language capable of encoding recursive, resource-constrained, and adaptive systems. The proposed Viable System Language (VSL) integrates cybernetic principles, including Ashby’s Law of Requisite Variety, with formal system design and execution semantics.
We show that VSL defines a constrained subspace of possible computational rules, analogous to a global rule space, restricted by viability axioms. The framework incorporates escalation mechanisms that operationalize incompleteness, enabling systems to handle unresolved or undecidable states through hierarchical propagation.
Additionally, we explore the relationship between VSL and autopoietic theory, proposing a layered architecture in which self-modifying subsystems can emerge under controlled constraints. A prototype runtime architecture is outlined, combining deterministic execution layers with bounded use of language models.
This work positions VSL as a bridge between cybernetics, theoretical computer science, and adaptive system engineering.
\end{abstract}
% -----------------------------------
% 1. INTRODUCTION
% -----------------------------------
\section{Introduction}
Modern computational systems increasingly operate under conditions of uncertainty, scale, and resource constraints. Traditional architectures often struggle to maintain coherence when faced with high variability environments.
The Viable System Model (VSM), originally proposed in cybernetics, provides a conceptual framework for understanding how systems maintain identity through recursive organization and regulation. However, VSM has historically remained descriptive rather than executable.
This work introduces the \textit{Viable System Language (VSL)}, a formal language designed to encode VSM structures as computational systems. The goal is to bridge the gap between conceptual system theory and executable architectures.
We propose:
\begin{itemize}
    \item A formal syntax and grammar for VSM-based systems
    \item A set of axioms defining viability constraints
    \item An operational semantics enabling execution
    \item A hybrid runtime architecture combining deterministic processes and language models
\end{itemize}
% -----------------------------------
% 2. BACKGROUND
% -----------------------------------
\section{Background}
The Viable System Model defines five interacting subsystems responsible for operations, coordination, control, intelligence, and policy. Its recursive nature allows systems to be composed hierarchically.
Ashby’s Law of Requisite Variety establishes that a system must match the complexity of its environment to remain stable. This principle is central to our formalization.
Autopoietic theory introduces the notion of systems that self-produce and maintain their identity through internal processes. While full autopoiesis is not assumed, it informs our layered autonomy model.
From theoretical computer science, incompleteness and computability constraints imply that no sufficiently expressive system can resolve all internal states. We incorporate this limitation explicitly through escalation mechanisms.
% -----------------------------------
% 3. FORMAL LANGUAGE
% -----------------------------------
\section{Formal Language}
\subsection{System Definition}
A viable system is defined as:
\begin{equation}
V(id, L) ::= \langle S1, S2, S3, S4, S5, E \rangle
\end{equation}
where each subsystem fulfills a specific regulatory role.
\subsection{Axioms}
We define a set of core axioms:
\begin{itemize}
    \item \textbf{Recursion:} operational units are themselves viable systems
    \item \textbf{Budget constraint:} resources decrease monotonically across levels
    \item \textbf{No direct coupling:} communication occurs through coordination layers
    \item \textbf{Requisite variety:} system variety must match environmental variety
    \item \textbf{Escalation:} unresolved signals propagate upward
\end{itemize}
\subsection{Channels}
Upward and downward communication is defined as:
\begin{align}
\phi^{\uparrow} &: V_{i}(L+1) \rightarrow S3(L) \\
\phi^{\downarrow} &: S3(L) \rightarrow V_{i}(L+1)
\end{align}
% -----------------------------------
% 4. OPERATIONAL SEMANTICS
% -----------------------------------
\section{Operational Semantics}
We define system execution as discrete transitions over time.
\subsection{State Transition}
\begin{equation}
\langle V, state_t \rangle \rightarrow \langle V, state_{t+1} \rangle
\end{equation}
\subsection{Execution Cycle (Tick)}
\begin{lstlisting}
tick(L):
  read upward signals
  apply coordination (S2)
  apply regulation (S3)
  update parameters
  execute operations (S1)
\end{lstlisting}
\subsection{Escalation Condition}
\begin{equation}
resolve(s, V) = \emptyset \land urgency(s) > \tau \Rightarrow s \uparrow
\end{equation}
% -----------------------------------
% 5. VIABILITY AS CONSTRAINT SPACE
% -----------------------------------
\section{Viability as Constraint Space}
We interpret VSL systems as trajectories within a constrained rule space.
\begin{equation}
VSF\_space = \{ r \mid r \text{ satisfies viability axioms} \}
\end{equation}
This defines a subset of all possible computational systems restricted by viability conditions.
% -----------------------------------
% 6. INCOMPLETENESS AND ESCALATION
% -----------------------------------
\section{Incompleteness and Escalation}
We assume the existence of unresolved signals:
\begin{equation}
\exists s : resolve(s, V) = \emptyset
\end{equation}
Escalation acts as a structural mechanism to handle such cases:
\begin{equation}
s \Rightarrow \phi^{\uparrow}
\end{equation}
This provides a practical resolution path for undecidable states.
% -----------------------------------
% 7. LAYERED AUTOPOIESIS
% -----------------------------------
\section{Layered Autopoiesis}
We define a layered autonomy model:
\begin{itemize}
    \item Root systems remain human-governed
    \item Subsystems may generate internal rules under constraints
\end{itemize}
This enables controlled self-modification without compromising global stability.
% -----------------------------------
% 8. PROTOTYPE IMPLEMENTATION
% -----------------------------------
\section{Prototype Implementation}
We implemented a prototype architecture consisting of:
\begin{itemize}
    \item Signal extraction via instrumented pipelines
    \item Coordination and regulation in Python-based services
    \item Cognitive processing layers using language models
    \item Structured communication via JSON-based channels
\end{itemize}
The system operates under explicit resource constraints and supports hierarchical escalation.
% -----------------------------------
% 9. DISCUSSION
% -----------------------------------
\section{Discussion}
The proposed framework introduces a new perspective on system design:
\begin{itemize}
    \item Viability replaces correctness as the primary objective
    \item Escalation operationalizes incompleteness
    \item Hybrid execution balances determinism and adaptability
\end{itemize}
Limitations include incomplete formal semantics and the need for empirical validation.
% -----------------------------------
% 10. CONCLUSION
% -----------------------------------
\section{Conclusion}
We introduced a formal language for encoding viable systems as executable computational structures. By integrating cybernetic principles with formal semantics, we provide a foundation for building adaptive, resource-aware systems.
Future work includes completing the operational semantics, developing interpreters, and exploring fully autonomous subsystems.
